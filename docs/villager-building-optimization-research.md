# 太吾村村民培养与建筑产出优化调研

> 最后核对：2026-07-11  
> 适用范围：当前本机游戏版本与程序集  
> 主要证据：运行中 UI/MCP 探针、前端 `Assembly-CSharp.dll`、后端 `GameData.dll`、共享类型 `GameData.Shared.dll`

## 1. 调研目标

本 Mod 的目标不是简单地按单项数值排序村民，而是在两类目标之间做可解释的分配：

1. **短期产出**：尽快获得银钱、威望、物品或人才等建筑产出。
2. **长期培养**：利用建筑主事教授书页、提升学徒资质与造诣，为未来建筑经营培养人才。

这两个目标经常冲突。高造诣成年人放入经营岗位可以立即提高产出，但儿童、低资质或低造诣村民占用岗位时，当前收益可能下降，却可能获得更高的长期成长价值。

## 2. 人物范围

当前建筑经营候选可以分为三类：

| 类别 | 可任主事 | 可任学徒/伙计 | 当前经营贡献 | 培养价值 |
| --- | --- | --- | --- | --- |
| 成年太吾村民 | 是 | 是 | 有 | 有 |
| 儿童太吾村民 | 否 | 是 | 0 | 有，且适合长期培养 |
| 同道 | 否 | 否 | 不进入村内经营候选 | 不通过此系统培养 |

运行时检查酒楼的伙计候选缓存：

- 总候选 64 人；
- 成人 54 人；
- 儿童 10 人；
- 同道 0 人；
- 当前建筑已占用而被禁止重复选择 7 人。

前端 `BuildingManageSubPageShop.OpenSelectChar` 的逻辑与此一致：

- 主事位置只加入 `BuildingManageDisplayData.AvailableWorker`；
- 非主事位置额外加入 `AvailableChildren`；
- 数据最终通过 `TaiwuDomainMethod.AsyncCall.GetVillagersForWorkDisplayData` 转换为候选行。

## 3. 原生经营 UI

酒楼、百家宴等建筑复用 `BuildingManageSubPageShop`。页面包含：

- 1 个主事位；
- 最多 6 个伙计/学徒位；
- 当前经营进度和预计产出；
- 主事身份、资质、造诣、传道授业等级、工作效率；
- 学徒造诣、剩余潜力、已读书页、工作效率、儿童标记；
- 培养记录；
- 快速派遣、快速撤免、自动派遣和三套派遣方案。

原生快速派遣规则：

### 主事

- 造诣最高；
- 资质最高；
- 修习最多；
- 可限制“符合身份”；
- 可锁定人物。

### 学徒

- 造诣最高；
- 资质最高；
- 资质最低；
- 修习最少；
- 可排除身份；
- 可允许儿童；
- 可排除潜力已尽；
- 可排除无可研读；
- 可锁定人物；
- 可指定 1 至 6 人。

原生系统只做单栋建筑内的局部排序，不能处理跨建筑的人才竞争和周期阈值，因此仍有明确的 Mod 空间。

## 4. 身份与教学

建筑配置通过 `BuildingBlockItem.VillagerRoleTemplateIds` 指定匹配身份。

身份匹配与经营效率是两件不同的事：

- **经营效率**主要由对应技能造诣决定；
- **身份匹配**决定主事是否满足“为人师表”，即能否按建筑规则教授学徒；
- 手动指派一个身份不匹配的人并不等于其造诣贡献消失，但会损失教学价值；
- UI 的 `BuildingManagerLeaderView` 使用 `VillagerRoleCharacterDisplayData.MatchVillagerRole` 显示身份匹配状态，并允许通过太吾氏祠堂授予/撤销身份。

已确认的两套对应关系：

| 技能体系 | 基础建筑 | 匹配身份 | 相关性格 |
| --- | --- | --- | --- |
| 厨艺 | 食窖 | 农户 | 合道 |
| 医术 | 药房 | 大夫 | 冷静 |

## 6. 工作效率与每月进度

以下公式适用于酒楼、百家宴等使用总造诣的普通经营建筑。

当前全局常数：

```text
ShopManageProgressBaseDelta = 650
BuildingTotalAttainmentFinalDivisor = 3
AgeAdult = 16
TaiwuVillagerMaxPotential = 36
```

### 6.1 岗位贡献

```text
主事贡献 = 150 + 主事对应技能造诣

成年伙计合计贡献 =
    floor(sum(50 + 每名伙计对应技能造诣) / 3)

儿童贡献 = 0

建筑总造诣 = 主事贡献 + 成年伙计合计贡献
```

UI 会把单个伙计显示为 `(50 + 造诣) / 3` 的整数百分比，但后端计算建筑总值时是先求和再整体除以 3；极端情况下两种显示口径会产生 1 至 2 点取整差异。

代码还会检查 `DomainManager.Taiwu.CanWork(characterId)`。受伤、外部关系状态或其他原因导致不能工作时，该人物可能不贡献进度。

### 6.2 每月进度

```text
基础每月进度 = 650 + 建筑总造诣

最终每月进度 =
    基础每月进度 × 太吾村 ShopProgressBonus
```

这里必须区分“没有指派主事”和“已指派主事、但主事当前不能工作”：

- 建筑要求主事且主事槽为空时，`CanUpdateShopProgress` 返回 false，本月不推进；
- 已指派主事但该人物当前 `CanWork=false` 时，人物的造诣贡献为 0，但建筑仍可通过校验，普通经营建筑会以基础值 650 推进；
- `NeedLeader=false` 的建筑可以在没有主事时使用基础进度；
- 食窖、药房属于另一种情况：它们本身没有周期进度。

## 7. 离散周期与溢出

后端 `BuildingBlockData.OfflineChangeShopProgress` 会把进度钳制在上限；产出结算后调用 `OfflineResetShopProgress()`，直接重置为 0。超出的进度不会进入下一轮。

稳定状态下：

```text
完成月数 = ceil(进度上限 / 最终每月进度)
```

希望在 `N` 个月内完成时，硬阈值为：

```text
目标每月进度 = ceil(进度上限 / N)
```

### 7.1 酒楼/熟药铺：800

| 周期 | 最低每月进度 |
| ---: | ---: |
| 1 月 | 800 |
| 2 月 | 400 |

只要有一个有效成年主事，即使其造诣为 0：

```text
650 + (150 + 0) = 800
```

因此酒楼、熟药铺在正常规则下，有效主事已经足够达到每月一次。更多成年伙计不会继续缩短周期。

UI 的预测文本会使用 `Math.Min(delta, max)`，所以即使实际每月进度为 1290，也只显示 `+800/800`。这会隐藏进度溢出，Mod 应展示真实进度和溢出值。

### 7.2 争妍阁/病坊：1600

| 周期 | 最低每月进度 |
| ---: | ---: |
| 1 月 | 1600 |
| 2 月 | 800 |

任何有效主事通常都能保证两个月完成；只有建筑总造诣达到 950，才能把基础进度推到 1600，实现每月一次。

### 7.3 百家宴/药师馆：4800

| 周期 | 最低每月进度 |
| ---: | ---: |
| 1 月 | 4800 |
| 2 月 | 2400 |
| 3 月 | 1600 |
| 4 月 | 1200 |
| 5 月 | 960 |

`1599` 与 `1600` 的差异不是 1 点，而是稳定产出周期从 3 个月退化到 4 个月：

```text
ceil(4800 / 1600) = 3
ceil(4800 / 1599) = 4
```

因此分配算法应优先跨越周期阈值，而不是盲目最大化所有建筑的线性效率。

## 8. “溢出”并非总是完全浪费

超过周期阈值的进度不会结转，但建筑总造诣还可能影响单次产出的数量、价格、品质或招募结果。

需要把两个边际收益拆开：

```text
周期边际收益：是否跨过 ceil(MaxProgress / N) 的阈值

单次产出边际收益：周期不变时，更多总造诣是否改善本次结果
```

当前后端确认的主要类型：

### 售卖物品，如酒楼、熟药铺

售卖价格使用造诣因子：

```text
售卖造诣因子 = 40 + 建筑总造诣 / 50
```

因此酒楼达到每月一次后，继续增加造诣仍可能提高菜肴售价，只是不再提高产出频率。

### 直接产生银钱或威望

`BuildingProduceDependencyData` 的银钱/威望公式直接包含 `TotalAttainmentFactor`。这类建筑的总造诣通常继续线性影响单次收益。

### 物品、引子或人才招募

不同事件使用不同规则：

- 物品成功率可能加入 `BuildingTotalAttainment / 30`；
- 物品品级概率可能加入平均造诣 `/ 20`；
- 人才招募会把建筑总造诣加入招募评分；
- 赌博类特殊建筑另有成功/失败倍率，不能套用普通公式。

所以“达到周期阈值后撤人”只是一个候选策略，不能在所有建筑上直接视为最优。

## 9. 培养机制

每次建筑培养更新会处理最多 6 名学徒。

### 9.1 资质成长

学徒剩余潜力来自全局上限 36。每次培养会消耗潜力，并存在多条资质提升路径：

- 已消耗潜力达到固定节奏时的基础提升；
- 学徒对应性格带来的概率提升；
- 主事资质高于学徒资质时带来的概率提升；
- 太吾村建筑效果 `ShopManagerQualificationImproveRate` 的倍率。

主事与学徒资质差越大，相关提升概率通常越高。因此长期培养算法不能只看主事当前造诣。

### 9.2 书页与造诣

教学会检查：

- 是否存在主事；
- 主事身份是否满足教学规则；
- 主事掌握了哪些对应技能书页；
- 学徒尚未掌握哪些书页；
- 学徒当前造诣；
- 建筑要求的性格值；
- 主事可教授品级。

前端已经获得 `ShopBuildingTeachBookData`，其中包含：

- `TeachBookResult`；
- 主事可教授书页数量；
- 学徒已学书页数量；
- 可教授的具体书页。

## 10. 优化模型草案

### 10.1 产出优先模式

建议先满足离散周期阈值，再比较单次产出边际收益：

1. 为每栋建筑计算当前完成月数；
2. 计算跨到下一周期档位还差多少进度；
3. 优先用最小人员成本跨过价值最高的阈值；
4. 对已经无法继续缩短周期的建筑，计算单次产出增益；
5. 将剩余人力分配给边际收益最高的建筑。

需要展示：

- 真实每月进度；
- UI 隐藏的溢出进度；
- 当前周期与下一阈值；
- 增减某人的周期变化；
- 单次产出变化；
- 被调走人物对原建筑造成的损失。

### 10.2 培养优先模式

候选评分应至少考虑：

- 主事身份是否匹配；
- 主事可教授书页数量和最高品级；
- 主事与学徒的资质差；
- 学徒剩余潜力；
- 学徒未读书页数量；
- 学徒相关性格；
- 学徒年龄，尤其是儿童距离成年时间；
- 占用该人物造成的当前产出机会成本。

食窖、药房等无周期建筑应优先作为低机会成本培养场所。

### 10.3 混合模式

混合模式不应简单地将两个分数相加。更合理的方式是先设置产出约束：

```text
保证关键建筑不跌破指定周期阈值
```

然后在剩余岗位中最大化培养价值。例如：

- 酒楼只保留足以维持一月一产的最低配置；
- 百家宴优先达到 1600，保证三月一产；
- 剩余儿童放入食窖、药房等纯培养槽；
- 若额外造诣对单次收益很高，再决定是否保留高造诣伙计。

- `ShopProgressBonus`、挑战模式对各周期阈值的精确影响；

- 不能工作的临时状态应如何预测持续时间；

- 自动派遣与 Mod 批量方案之间的冲突处理。

## 13. 当前结论

这个问题本质上不是“把最高造诣的人塞进最高级建筑”，而是一个带离散阈值、岗位冲突、成长状态和多种产出函数的全局分配问题。

最重要的建模原则是：

1. 将周期阈值与单次产出收益分开；
2. 将成年人经营贡献与儿童培养价值分开；
3. 将身份教学能力与造诣经营能力分开；
4. 将首次结算时间与长期稳定周期分开；
5. 在跨建筑调人时计算机会成本，而不是只看目标建筑收益。
