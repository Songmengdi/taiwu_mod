# 太吾村村民与建筑全局优化：计算策略

> 状态：机制设计稿  
> 核对日期：2026-07-11  
> 目标版本：V1 计算并预览四套方案；V2 自动落地；V3 每月自动重算并调整

## 1. 结论

本 Mod 不应给每个人或每栋建筑计算一个混合“综合分”。游戏存在明显的离散周期、库存约束、不同产出公式和跨建筑人员竞争，把它们压成一个线性分数会产生错误结论。

正确的计算方式是：

1. 从游戏配置与当前存档生成完整快照；
2. 为每栋建筑枚举少量有意义的用人方案；
3. 用原生公式预测每个方案造成的本月状态变化；
4. 对四种目标分别做全村人员互斥的全局组合优化；
5. 向用户展示结果、变化原因、假设和风险，而不是只展示一个不可解释的分数。

四套方案的主目标互不混合：

| 方案 | 后台求解目标 | 决策周期 | UI 输出 |
| --- | --- | ---: | --- |
| 资产收益 | 实际银钱与月末银钱进度价值最大 | 本月 | 本月人员安排方案 |
| 人才培养 | 确定/期望成长最大 | 本月 | 本月人员安排方案 |
| 威望收益 | 实际威望与月末威望进度价值最大 | 本月 | 本月人员安排方案 |
| 招人收益 | 新增人物与月末招募状态价值最大 | 本月 | 本月人员安排方案 |

这里的“本月”是决策周期：方案只负责当前月的岗位，不要求用户连续维持 4 个月或 12 个月。月结后重新读取真实状态，再求下一月。尚未在本月结算的进度也不是零价值，而是作为月末状态的一部分计入对应目标。

不同目标之间只使用明确的次级排序规则，不使用任意兑换率，例如不规定“1 点资质等于 100 银钱”。


### 2.2 可直接复用的原生接口

- `GetBuildingManageDisplayData`：当前建筑经营、候选人、造诣、教学、收益等综合数据；
- `GetVillagerCharDisplayDataList`：完整村民人物数据；
- `GetVillagersForWorkDisplayData`：把候选人物转换为工作选择 UI 所需数据；

- `GetShopBuildingTeachBookData`：读取当前真实组合的可教学书页。

V1 还需要一个只读的后端预览方法。它接收“假设的主事与学徒组合”，复用原生配置和纯计算函数，但不得写入人物、建筑、随机数状态或存档。

## 3. 建筑不是白名单，而是配置驱动分类

当前版本共有 318 条 `BuildingBlock` 配置，其中 147 条与经营或培养有关，94 条使用周期进度。已观察到的功能分布包括：材料 34、银钱 20、招人 19、威望 17、研读 30、突破 14、物品 3、其他 10。

分类器应读取以下字段：

- `IsShop`
- `NeedShopProgress`
- `NeedLeader`
- `CanMakeItem`
- `IsCollectResourceBuilding`
- `FuncType`
- `MaxProduceValue`
- `RequireLifeSkillType` / `RequireCombatSkillType`
- `RequirePersonalityType`
- `VillagerRoleTemplateIds`
- `SuccesEvent` / `FailEvent`

再读取 `ShopEventItem`：

- `ResourceGoods`
- `ExchangeResourceGoods`
- `ItemList`
- `ItemGradeProbList`
- `RecruitPeopleProb`
- `ResourceList`
- `ShopEventType`
- `BuildingCore`

由此生成以下计算器类型：

| 计算器 | 典型建筑 | 主要机制 |
| --- | --- | --- |
| ResourceCollect | 堤堰、矿井、树农等 | 等级、生产力、依赖、总造诣共同决定资源 |
| DirectMoney | 镖局、乐坊、市集等 | 每次直接产生银钱 |
| SellItem | 酒楼、熟药铺、铁匠铺等 | 消耗指定可售物品，售价受造诣影响 |
| DirectAuthority | 知客亭、百戏园等 | 每次直接产生威望 |
| SellItemAuthority | 四海府、病坊、争妍阁等 | 售物并产生威望 |
| Recruit | 百家宴、药师馆、贤士馆等 | 累积招募分并生成候选人物 |
| ItemList | 茶园、蒸酒坊等 | 多个物品概率判定后择一 |
| ItemGrade | 当铺 | 按平均造诣修正品级概率 |
| TrainingOnly | 食窖、药房及大量研读/突破建筑 | 无周期产出，但可教学或有其他交互 |
| SpecialOverride | 藏书阁、赌坊、青楼等 | 使用建筑模板专用逻辑 |

任何无法识别的事件必须标记为“暂不参与自动优化”，保留当前指派并在预览中警告；不能猜测其收益。

## 4. 快照模型

一次求解只使用同一个月度时点的不可变快照。

### 4.1 人物快照

每个人至少包含：

- 人物 ID、年龄、成人/儿童、是否同道、是否属于太吾村；
- 原生候选接口给出的可指派资格；
- 当前 `CanWork`、受伤或其他临时状态；
- 16 项生活/战斗资质和造诣；
- 性格值；
- 已用/剩余培养潜力；
- 身份模板及身份是否匹配建筑；
- 已掌握书页；
- 当前岗位和用户锁定状态。

同道不由本系统安排。儿童可以作为学徒，但工作进度贡献为 0，不能成为主事。

### 4.2 建筑快照

- `blockKey`、模板 ID、等级、规模、生产力、可用状态；
- 当前进度与有效进度上限；
- 当前主事和最多 6 名学徒；
- 原生依赖是否满足；
- 产出仓位、招募缓存是否已满；
- 售物槽、物品类型、数量与可持续补货量；
- 安定/文化等依赖值及全部建筑效果倍率；
- 当前挑战模式和 `BuildingWorkHard` 等原生修正结果。

有效进度上限必须调用原生计算，不能把 800、1600、4800 写死；这些只是当前常见档位。

### 4.3 用户约束

- 锁定人物：保持原岗位或禁止安排；
- 锁定建筑：不修改全部岗位；
- 保留空闲人数；
- 是否允许儿童培养；
- 是否允许调动当前主事；
- 决策周期固定为本月；
- 库存策略：按现有库存，或假设用户及时补货；
- 收取策略：按当前仓位，或假设及时收取。

## 5. 共同公式

### 5.1 工作造诣

普通使用总造诣的建筑：

```text
主事贡献 = 150 + 主事对应技能造诣

成人学徒合计贡献 =
    floor(sum(50 + 每名成人学徒对应技能造诣) / 3)

儿童贡献 = 0

总造诣 A = 主事贡献 + 成人学徒合计贡献
```

只有 `CanWork=true` 的人物贡献工作造诣。部分配置通过公式参数要求 `MaxAttainment`，此时只使用 `150 + 主事造诣`；平均造诣类也必须走原生选择逻辑。

需要主事但主事槽为空时，建筑不推进。主事已存在但暂时不能工作时，其贡献为 0，建筑仍可能以基础进度推进。教学逻辑另有校验，不能把“工作贡献”和“能否教学”混为一谈。

### 5.2 进度与离散周期

普通建筑每月原始进度：

```text
D = (650 + A) * ShopProgressBonus
```

藏书阁等特殊模板不使用 650 基础值。所有倍率、取整和挑战修正以原生函数为准。

若当前进度为 `P`、有效上限为 `M`、本月进度为 `D`，本月状态转移为：

```text
若 P + D < M：本月无结算，P_end = P + D
若 P + D >= M：本月结算一次，P_end = 0，溢出丢弃
```

以下公式只用于 UI 解释“按当前效率还需几个月完成”，不作为默认求解周期，也不代表本月方案会连续执行那么久：

```text
首次完成所需月数 first = ceil((M - P) / D)
后续稳定周期 steady = ceil(M / D)

H 个月内完成次数：
N(H) = 0                                  , H < first
N(H) = 1 + floor((H - first) / steady)    , H >= first
```

每次产出后进度归零，溢出不继承。因此 `1599 -> 1600` 对 4800 上限建筑可能把预计完成时间从 4 个月缩短到 3 个月。优化器仍只提交本月配置，但必须正确评价本月留下的进度状态，不能只看是否当月结算。

### 5.3 随机修正

普通产出随机因子配置为 80% 到 120%。若调用路径使用 Redzen 的 `Next(80, 120)`，实际离散值为 80 到 119，期望为 99.5%，不能直接假设为 100%；仍应在每个具体产出函数中核对它传入的上下界和取整位置。

预览只计算期望与分布，不消耗游戏 RNG。特殊成功/失败建筑使用专用概率树。

## 6. 资产收益方案

### 6.1 指标

主目标：本月实际进入太吾资源账目的期望银钱，加上本月形成的月末银钱进度价值，合计最大。

只计算“本月实际到账”会把所有尚未跨过结算线的建筑错误判成零收益，因此使用一步状态价值：

```text
本月资产决策价值 =
    本月实际到账银钱
    + Φ_money(月末状态)
    - Φ_money(月初状态)

Φ_money(未完成建筑) =
    当前进度 / 有效进度上限
    * 该建筑下一次结算的参考期望银钱
```

参考期望银钱只用于衡量已积累进度，按建筑当前非人员条件和一个明确显示的参考结算方案计算。本月跨线时，使用本月真实人员计算实际产出，结算后进度归零。UI 必须把“本月到账”和“进度价值”分开，不能把后者伪装成已经获得的银钱。

不把以下内容错误计入成本：原生村民分成是额外生成给个人的资源，不从建筑总产出扣除。V1 暂不把待售物品的机会成本折算为银钱，因为缺少统一、可靠的市场兑换模型；改为单独展示“消耗物品清单”。

### 6.2 直接银钱

每次基础产出：

```text
MoneyOutput =
    300
    * Productivity / 100
    * SafetyCulture / 100
    * TotalAttainmentFactor / 100
    * GainResourcePercent / 100
```

之后应用银钱增益和随机修正。本月若完成结算，就计算一次真实期望产出；否则只增加月末进度价值。仓位已满时严格按原生状态判断能否推进。

### 6.3 售物银钱

```text
SaleAttainmentFactor(A) = 40 + A / 50

SalePrice(basePrice) =
    basePrice
    * SaleAttainmentFactor(A) / 100
    * Productivity / 100
    * Safety / 100
    * GainPercent / 100
```

再应用随机修正和银钱增益。没有合法售物时建筑不会推进。选择不同物品会改变基价和机会成本，必须作为不同的建筑候选方案枚举；本月是否能结算一次，以真实库存和状态转移为准。

### 6.4 资源建筑

如果“资产”只指银钱，资源建筑不进入主目标，只在完全同分时作为次级收益展示。若以后增加“综合物资”模式，应让用户明确选择资源价值表，不能偷偷使用任意汇率。

### 6.5 排序规则

按以下字典序比较全局方案：

1. 本月资产决策价值；
2. 其中本月实际到账银钱更多；
3. 更少物品消耗；
4. 更少调动人物；
5. 更多空闲成人。

## 7. 威望收益方案

威望方案与银钱方案独立求解，不把银钱作为主分数。它采用相同的一步状态模型：

```text
本月威望决策价值 =
    本月实际到账威望
    + Φ_authority(月末状态)
    - Φ_authority(月初状态)
```

直接威望基础公式：

```text
AuthorityOutput = MoneyBuildingOutput / 10
```

其余倍率、随机与建筑效果照原生顺序应用。售物威望建筑同样受到库存限制。

字典序：

1. 本月威望决策价值；
2. 其中本月实际到账威望更多；
3. 更少物品消耗；
4. 更少调动；
5. 更多空闲成人。

## 8. 招人收益方案

### 8.1 原生招募状态转移

每次完成时，以当前招募累计分 `S` 和总造诣 `A` 计算两个等概率分支：

```text
S' = S + 0.8 * A
或
S' = S + 1.2 * A
```

在阈值 `[100, 200, 300, 500, 700, 900, 1200, 1600, 2100]` 中选择 `S'` 严格大于的最高品级阈值，生成一个该品级候选，并扣除对应阈值；剩余分保留到下一次。招募缓存已满时不会继续产出。

### 8.2 精确动态规划

本月若完成招募事件，对这一次事件展开离散状态 DP：

```text
state = (剩余招募分, 各品级人数, 已占缓存数)
```

每一步展开 0.8 和 1.2 两个分支并合并相同状态，可得到精确的：

- 期望招募人数；
- 各品级概率分布；
- 至少获得某品级人物的概率；
- 期末剩余招募分。

人物具体资质还受到建筑的 `RecruitLifeSkillsAdjust`、`RecruitCombatSkillsAdjust` 和人物生成随机影响。预览可用隔离、固定种子的 Monte Carlo 调用纯生成人物逻辑，输出资质分布；绝不能写入真实招募缓存或消耗存档 RNG。

### 8.3 “最高招人收益”的确定含义

默认使用原生阈值作为品级价值，避免发明兑换率。本月没有完成事件时，建筑进度也保留状态价值：

```text
RecruitValue = Σ(各品级人数 * 对应原生阈值)
             + 期末剩余招募分

Φ_recruit_building =
    当前建筑进度 / 有效进度上限
    * 下一次招募事件的参考招募分价值
```

这等价于最大化被转化和保留的原生招募分，同时保留真实的品级跃迁。比较规则：

1. 本月新增 `RecruitValue`，包括人物、剩余招募分和建筑事件进度价值；
2. 更高品级分布优先，从最高品级向下做随机占优比较；
3. 期望人数更多；
4. 用户若指定目标技能，则比较该技能资质分布；
5. 更少调动。

UI 必须同时展示人数和品级分布，不能只显示 `RecruitValue`，否则用户会误解“一个高品级”和“多个低品级”的取舍。

## 9. 人才培养方案

培养不能用“主事造诣高 + 学徒资质低”这样粗略的线性分数。它由资质随机增长、书页教学、潜力消耗和机会成本组成。

### 9.1 教学资格

主事必须拥有与建筑 `VillagerRoleTemplateIds` 匹配的身份，建筑才可教学。每栋建筑最多处理 6 名学徒。纯培养建筑没有周期产出，是默认的低机会成本教室。

当前后端教学路径未使用 `CanWork` 过滤主事和学徒；实现时应忠实预测原生结果，同时在人物临时不可工作时给出提示，避免与 UI 直觉冲突。

### 9.2 单月资质增长的精确期望

当学徒已用潜力 `p < 36` 时，依次执行三条提升路径：

1. 若 `p != 0 && p % 4 == 0`，确定提升 1；
2. 性格概率：`personality / 3 * QualificationImproveBonus`；
3. 师生资质差概率：`(leaderQualification - studentQualification) * 3 * QualificationImproveBonus`。

每次成功都立即使基础资质 `+1`，因此前一步会改变后一步的师生差。之后已用潜力增加 1。预测器必须按执行顺序展开概率树，而不是简单把三个概率相加。

原生 `RedzenHelper.CheckPercentProb` 的语义已经确认：`percentProb <= 0` 必定失败；正数时判断 `Next(100) < percentProb`，因此 1 到 99 是相应百分比，100 及以上必定成功。

对每个 `(主事, 学徒, 技能)` 组合，输出：

- 下一月资质增长的完整分布；
- 期望资质增长；
- 是否消耗最后一格潜力；
- 每点期望增长对应的潜力消耗。

### 9.3 书页与造诣成长

对当前真实指派可直接读取 `GetShopBuildingTeachBookData`。对假设组合，预览后端应镜像原生生活/战斗书页教学判断，得到本月可教书页集合。

主事可以教、学徒尚未掌握、且满足品级等条件的每一页都应逐页模拟。学习点使用：

```text
LearningPoint = 当前相关造诣 * (100 + 相关性格) / 100
```

最终造诣变化、页掌握状态和取整由原生逻辑计算。书页价值不按页数简单相加，应至少输出：

- 新掌握书页数；
- 新增造诣；
- 解锁的最高品级；
- 下一月仍可教学的剩余页数。

### 9.4 培养目标的字典序

默认“最高人才培养收益”比较：

1. 本月期望资质增长总点数；
2. 本月确定获得的资质点数；
3. 本月通过书页获得的造诣增长；
4. 新掌握书页数与最高品级；
5. 受益学徒人数；
6. 剩余可培养路径更多；
7. 占用周期产出岗位造成的机会损失更小；
8. 调动更少。

如果用户选择“重点培养某人/某技能”，先限制受益人物和技能，再使用同一字典序。儿童不获得工作进度，但可获得培养收益，因此在纯培养教室中通常有较高优先级；这仍由实际概率树与书页结果决定，而非固定儿童加分。

培养只精确预测本月，因为随机资质增长、书页状态和身份会逐月改变。UI 可显示未来“潜力上界”，但不得把它标成当前方案的精确收益。月结后重新求解下一月。

## 10. 全局求解器

### 10.1 建筑局部方案枚举

直接枚举所有人物排列会爆炸。每栋建筑先生成有代表性的局部候选：

- 当前方案；
- 最少人数跨越每个进度档位的方案；
- 每种事件单次产出最高的若干方案；
- 合法教学主事配最佳学徒组；
- 不派人或只派主事；
- 用户锁定产生的固定方案。

利用支配关系删枝：如果方案 X 使用的人是 Y 的超集，且所有主指标、次指标都不优于 Y，则删除 X。对 800 上限建筑尤其要保留“仅主事已达每月完成”和“继续加人提高单次售价”的两种非支配方案。

### 10.2 全村组合

每栋建筑选择至多一个局部方案，每个村民至多出现在一个建筑岗位：

```text
choose one plan per building
subject to person assignment count <= 1
           locks and eligibility
maximize objective lexicographically
```

实现建议使用确定性的分支定界：

1. 优先处理候选少、收益差异大的建筑；
2. 用各剩余建筑独立最优值之和作为上界；
3. 人物冲突后动态收紧上界；
4. 对字典序目标逐层固定最优值；
5. 达到时间预算时返回当前最好解和可证明上界差距。

若性能不足，可先用贪心构造可行解，再做人物交换、建筑方案替换和 2-opt 局部改进作为下界，但 UI 应诚实标记为“近似最优”。只有求解完成或上下界相等时才标记“当前模型下最优”。

### 10.3 为什么不能只逐栋贪心

同一个高造诣村民可能让百家宴跨过 1600 阈值，也可能显著提高酒楼售价。逐栋选择会重复占用他，并忽略把一个人从 1599 推到 1600 的收益远大于把另一个建筑从 1200 推到 1300。必须在全村范围同时比较边际结果。

## 11. 特殊建筑扩展机制

计算器注册表按稳定机制选择，而不是按中文名：

```text
generic calculators selected by config/event fields
template overrides selected by BuildingTemplateId
event overrides selected by ShopEventType or event id
```

已知需要覆写或额外核对：

- 藏书阁模板 105：进度增量不含基础 650；
- 赌坊、青楼：成功/失败分支、补偿和倍率；
- 贤士馆：特殊招募属性修正；
- 当铺：品级概率事件；
- 制造类建筑：不是周期经营，不能按普通 ShopProgress 计算；
- 研读/突破类：可培养或提供专用功能，但不一定产生周期资源。

每当游戏更新出现未知字段组合，分类器记录诊断信息并保守跳过。这样建筑再多也不需要维护名称列表。

## 12. V1 预览界面：直接给出人员安排

收益公式、进度价值和概率分布属于后台求解过程，不是主界面的产品输出。用户选择“资产、培养、威望、招人”之一后，UI 直接给出该目标下的本月完整人员安排。

默认按建筑展示：

| 建筑 | 主事 | 学徒/伙计 | 相对当前的操作 |
| --- | --- | --- | --- |
| 建筑 A | 人物甲 | 人物乙、人物丙 | 甲调入；乙保留；丙调入 |
| 建筑 B | 人物丁 | 无 | 丁替换原主事 |

交互规则：

- 默认只展开需要变更的建筑，未变化建筑折叠显示；
- 明确区分主事和学徒/伙计，不只显示人物名字；
- 同一个人物只出现于一个岗位；
- 显示“调入、调出、保留、空置”四种操作；
- 锁定人物和锁定建筑原位保留，并显示锁定标记；
- 无法识别、条件不足或库存阻塞的建筑保持当前安排，并显示简短警告；
- 提供“按人物查看”，反向显示每名村民本月应该去哪里；
- V1 的主要动作是“预览方案”，V2 再增加“一键应用”。

计算结果可用于内部日志、测试和方案比较，但不要求玩家阅读收益报表才能完成排班。

V1 只预览，不改变存档。V2 在用户确认后逐项调用原生设置接口，操作前再次校验快照版本；若人物、建筑、库存或进度已变化则停止并要求重算，避免应用过期方案。V3 在月初或月度结算后重新取快照，只在预期收益改善超过用户阈值时调整，以减少无意义换岗。

## 13. 验证计划

### 13.1 公式单元测试

- 800、1600、4800 周期的边界：799/800、1599/1600；
- 当前进度非零和产出后归零；
- 无主事、不能工作的主事、成人学徒、儿童学徒；
- 总造诣先求和后除 3 的取整；
- 售物库存 0、1、足量；
- 招募阈值严格大于与剩余分结转；
- 潜力 0、4、35、36；
- 概率小于 0、等于 0、99、100、大于 100；
- 仓位已满与及时收取两种策略。

### 13.2 原生对照测试

在隔离测试存档中，为同一建筑设置固定人员，记录 UI 预测、月结前后进度和产出，与 Mod 预测逐项比较。随机结果不要求单次相等，但大量样本的均值和分布应落在置信区间内。

### 13.3 求解器测试

- 小规模实例用穷举验证全局最优；
- 构造两个建筑争抢同一高造诣人物；
- 构造跨阈值收益胜过线性收益的实例；
- 构造当前方案就是最优、锁定人物、无人可用；
- 对相同快照重复求解必须得到相同方案。

## 14. 尚需在编码阶段确认的机制

以下问题不会阻止总体模型，但在实现对应计算器前必须用后端反编译、只读预览调用或隔离存档实验确认：

1. 每类产出调用随机整数时传入的具体上下界，以及所有相关取整顺序；
2. 赌坊/青楼显示随机范围与实际随机修正不一致时，以哪条路径为准；
3. 招募缓存、产出仓位对连续多月的确切阻塞时点；
4. 假设组合的书页教学如何完整复用原生私有逻辑；
5. 建筑效果倍率叠加、取整和挑战模式的最终调用顺序；
6. 售物自动补货是否存在原生来源，若无则只能按真实库存预测。

这些项应通过“计算器未验证标志”暴露在开发诊断界面中。未验证的特殊建筑不得参与自动落地。
